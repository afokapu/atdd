## Scope

### In Scope

This issue prepares the per-LLM convention files at the repo root that every `atdd spawn` (`#K1`) launch references via Section 1 of the harness (`include: ${persona_convention_file}` per spec §7.1). Without this, the spawn harness embeds rule-ID context that the agent has no convention file to resolve against.

- **Per-LLM template files** at `src/atdd/coach/templates/persona/<llm>/<file>.md.tmpl` for each supported LLM:
  - `claude-code/CLAUDE.md.tmpl`
  - `codex/AGENTS.md.tmpl`
  - `glm/GLM.md.tmpl`
  - `gemini/GEMINI.md.tmpl` (or aliased to `AGENTS.md` per spec §7.1)
- **Generator integrated with `atdd sync`** — extends the existing toolkit-sync entry point so each repo regenerates the four files at the repo root from the templates. The integration mechanism is shared with `#P3` (sync per-LLM hookup); K4 owns the templates and the per-LLM extension; P3 owns the broader sync convention.
- **Rule-ID grammar embedded** — each generated file embeds the canonical rule-ID grammar `<archetype>.<convention_short_name>.<rule_name>` and at least one example rule-ID (e.g. `coder.dead-code.reachability`) per spec §7.1.
- **`bind_rule()` contract embedded** — each generated file embeds the contract example `bind_rule("<canonical_id>")` and the substrate-level expectation: validators MUST call `bind_rule` at module-import time, the named rule MUST exist in a convention's `rules:` block, with a reference to the rule-ID grammar contract anchor (e.g. `SPEC-COACH-RULEID-0007`).
- **Output files written at the repo root** — `CLAUDE.md`, `AGENTS.md`, `GLM.md`, `GEMINI.md` per spec §7.1.

### Out of Scope

- The broader `atdd sync` command behavior — owned by `#P3` (sync extensions). K4 only adds the per-LLM template-rendering path; P3 wires it into the sync convention.
- The substrate `bind_rule` implementation, rule registry, and `RuleMetadata` dataclass — already shipped (substrate v12); K4 only references them in the generated files.
- Convention files for non-LLM consumers (e.g. `OPERATOR.md`) — out of K4's scope; only LLM-persona files.
- `atdd spawn` CLI surface — owned by `#K1`. K4 is upstream prep so the spawn harness's Section 1 include resolves correctly.
- Other harness sections (`wmbt_rules:`, `train_rules:`, `security_rules:`) — owned by `#K2`. K4 ships the persona convention file that those blocks reference.
- Versioning of the convention files — out of scope; K4 ships the canonical version per spec §7.1.

### Dependencies

- `#K1` — `atdd spawn` is the consumer of the generated convention files; without K1 there is no production reader.
- `#P3` — sync integration is shared with this issue; the two issues coordinate the convention file generation path through `atdd sync`.
- `src/atdd/coach/templates/` — existing template directory for toolkit-sync output (the parent of the new persona/ subdirectory).
- Substrate v12: rule-ID grammar contract anchor and `bind_rule()` shape — already documented.

## Context

### Problem Statement

| Aspect | Current | Target | Issue |
|--------|---------|--------|-------|
| Per-LLM convention files | `CLAUDE.md` exists in some repos hand-maintained; `AGENTS.md`, `GLM.md`, `GEMINI.md` mostly absent or ad-hoc | All four files generated by `atdd sync` from canonical templates | Without canonical files, every spawned agent's harness-Section-1 include resolves to a different shape; rule-ID references become unresolvable |
| Rule-ID grammar in convention files | Today's `CLAUDE.md` files don't document the canonical grammar; agents don't know how to recognise rule-IDs | Each file embeds `<archetype>.<convention_short_name>.<rule_name>` with worked examples | Agents cite rule-IDs in commits and reviewer reports — if the grammar is undocumented, agents either invent shapes or omit rule-IDs entirely |
| `bind_rule()` contract documentation | The substrate-level expectation that validators call `bind_rule` at import time lives in convention YAMLs only | Each per-LLM file embeds the contract example and expectation, anchored to the spec | Agents that author validators (testers, coders) need the contract visible at the convention-file level so they don't drift from the substrate |
| Sync integration | `atdd sync` exists but does not yet handle per-LLM template rendering | `atdd sync` regenerates all four files from `src/atdd/coach/templates/persona/<llm>/<file>.md.tmpl` | Without sync integration, the templates are dead artifacts; the rendered files only stay current if hand-edited |

### User Impact

The "user" of this issue is every agent (planner, tester, coder, reviewer) under any of the four supported LLM personas. Per spec §7.1, the spawn harness's Section 1 begins with `include: ${persona_convention_file}` — the agent reads this file as part of every launch. If the file is missing, malformed, or absent of rule-ID guidance, the agent has no anchor for the rule-ID-rich blocks (`wmbt_rules:`, `train_rules:`, `security_rules:`) that follow.

Per spec §6.3, the reviewer's `rule_id_resolution` block instructs: "When you find a violation that matches a known rule, identify the canonical `rule_id` from the convention files (referenced in the bundled context). Use `atdd rules grep <pattern>` if needed." The "bundled context" is the persona convention file; without K4, the file does not document the grammar the reviewer is supposed to follow.

The lived pain today: in CI runs of the v8 coach prototype, reviewer agents emitted findings with hand-invented rule-ID-like strings (`PLAN-COVERAGE-001`, `TEST-CONTRACT-FAILURE`) that did not resolve through `bind_rule()`. The fix isn't to constrain the reviewer's freeform output (it can still emit `rule_id: null` per §7.4) — it's to make the canonical grammar visible in the persona convention file the reviewer reads on every launch. K4 is that fix.

### Design Anchor

K4 is template-driven generation, not literal file copy. The reason: as the rule-ID grammar evolves (new archetypes, new conventions), the templates change; running `atdd sync` regenerates the per-LLM files in every consuming repo. This pattern mirrors how `CLAUDE.md` itself is sync-generated today between the ATDD wrapper sections — K4 extends that pattern to the rule-ID-aware sections.

The choice to ship four distinct files (rather than one shared `AGENTS.md` symlinked everywhere) reflects spec §7.1's per-LLM convention file table: each LLM has its own naming convention (`CLAUDE.md` vs `GLM.md`) that operator workflows depend on. The Gemini case is explicitly aliased to `AGENTS.md` per spec §7.1 because that's the convention Codex established and Gemini interoperates with.
