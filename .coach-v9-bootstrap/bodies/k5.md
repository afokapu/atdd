## Scope

### In Scope

This issue operationalizes the "behavior parity" claim made by the orchestrate-absorbing issues — `#J4` (two-phase commit), `#K1` (spawn skeleton), `#K3` (canonical naming pass). Without K5, parity is a review-time judgment call; with K5, parity is CI-enforced byte-and-state equivalence across five fixture scenarios.

- **Test module** at `tests/integration/test_orchestrate_coach_parity.py` collecting at least five fixture scenarios as distinct pytest tests:
  1. Single issue
  2. Multi-issue with dependencies
  3. Resume case (after partial Phase A failure)
  4. Worktree creation failure with rollback
  5. Multiplexer-mode pane (vs workspace)
- **Each fixture defines** an `atdd orchestrate <args>` invocation and the expected `atdd coach <equivalent args>` invocation against shared fixture worktree state, a multiplexer mock backend, and a fake `gh` CLI returning fixed issue bodies.
- **Equivalence assertions on observable outputs**:
  - **Worktree creation** — identical order, paths, and branches between the two invocations.
  - **Multiplexer dispatch** — identical backend, mode, and surfaces created (per the mock backend's recorded calls).
  - **Canonical naming** — identical names applied to surfaces.
  - **Session prompts** — `.launch_prompt.txt` contents byte-equivalent (modulo a documented timestamp normalisation pass).
  - **State file mapping** — `orchestrate-state.json` (orchestrate) and `decisions.jsonl` (coach) carry semantically equivalent information per the field-by-field mapping in `tests/integration/parity-fixtures/orchestrate-coach.md`.
- **Allowed-differences are explicit** — state file format (jsonl vs single-doc json), additional logging, additional decision entries with no orchestrate equivalent (e.g. observer hookup events). The differences-allowed list is documented in `parity-fixtures/orchestrate-coach.md`.
- **Runtime budget** — the full suite runs in <60s on a developer machine so it can be a blocking CI check without slowing the merge pipeline.
- **CI gate** — failure of this suite blocks `#P5` (atdd orchestrate decommission) per spec §11.3.

### Out of Scope

- The `atdd babysit` parity test suite — owned by `#L8` (its own gating decommission for `#P6`). K5 only covers the orchestrate→coach equivalence.
- The `atdd orchestrate` decommission itself — owned by `#P5`. K5 is the gating proof; P5 removes the command and the absorbed-from-orchestrate machinery once K5 (and dependencies) pass.
- Substantive behavior changes between `atdd orchestrate` and `atdd coach` — by definition out of K5's scope. If the parity assertions require a coach-side fix to pass, the fix lands in the appropriate K-track issue (K1/K3) before K5 lands.
- Multiplexer real-backend testing (cmux/zellij/tmux as actual subprocesses) — K5 uses mock backends so the suite stays under the 60s budget. Real-backend smoke is `#Q1`'s concern.
- Performance benchmarks — K5 asserts equivalence, not absolute performance.

### Dependencies

- `#J4` — two-phase commit absorbed; without it, the worktree-creation-failure-with-rollback fixture has no coach side to test against.
- `#K1` — spawn skeleton; without it, there is no coach-side launch path.
- `#K3` — canonical naming pass; without it, the canonical-naming equivalence assertion has no coach-side behavior.
- `src/atdd/coach/commands/orchestrate.py` — today's `atdd orchestrate` command (still present pre-decommission).
- `src/atdd/coach/utils/multiplexer.py` — the abstraction whose mock backend the suite installs.
- A fake `gh` CLI / fixture issue bodies — small test fixture set, written as part of K5.

## Context

### Problem Statement

| Aspect | Current | Target | Issue |
|--------|---------|--------|-------|
| Orchestrate→coach behavior parity | Asserted by issue authors (J4, K1, K3) at review time; no CI enforcement | CI-enforced byte-and-state equivalence across five fixture scenarios | Without CI enforcement, drift between `atdd orchestrate` and `atdd coach` accumulates silently; the decommission in `#P5` becomes risky because no test catches the regression |
| State file mapping documentation | Implicit; reviewers must trust that `orchestrate-state.json` ↔ `decisions.jsonl` carry the same information | Explicit field-by-field mapping at `tests/integration/parity-fixtures/orchestrate-coach.md` is the suite's allowed-differences oracle | Without an explicit oracle, "allowed differences" devolves into per-test ad-hoc judgment calls |
| Decommission gate | `#P5` decommissions `atdd orchestrate`; today it depends on review-time parity claims | `#P5` cannot land until K5 passes on CI per spec §11.3 | Without the gate, `#P5` could land while orchestrate-coach divergence remains; recovery means re-introducing orchestrate, eroding the v9 design |
| Suite runtime | A long-running parity suite would be skipped in CI | <60s budget keeps it always-on | Per spec §11.3, parity must be continuously verified, not only at decommission time; the budget makes "always-on" feasible |

### User Impact

The "user" of this issue is the merge-cascade automation and the human reviewer who signs off on the orchestrate decommission PR. Today, the orchestrate-absorbing issues (J4, K1, K3) make a parity claim that no test backs. If `#P5` lands and a regression slips through, recovery requires re-introducing `commands/orchestrate.py`, which spec §0.2 (and the broader v9 architecture) explicitly forbids.

Per spec §11.3 ("Decommissioning `atdd orchestrate` and `atdd babysit` (Track P, #P5–#P6)"), the decommission has explicit prerequisites: "All orchestrate-absorbing issues land first" and "The parity test suite (`#K5`) passes on CI." K5 is the second of these; without it, the decommission inherits silent risk.

The lived precedent: prior decommissions in this codebase (e.g. legacy validators, deprecated CLI subcommands) sometimes shipped without a parity oracle and accumulated breakage detected only by external operators. K5 makes the oracle explicit before the decommission, so orchestrate's removal is a confident change rather than a hopeful one.

### Design Anchor

The five fixture scenarios are not arbitrary — they map to the five behavior surfaces orchestrate's two-phase commit specifically guards: single-issue happy path, multi-issue dependency ordering, resume after partial failure, rollback on Phase A failure, and the multiplexer mode the operator selects per workflow. Per spec §4.6, these are the surfaces orchestrate's design specifically guarantees; K5 asserts coach guarantees the same.

The choice of byte-equivalence for `.launch_prompt.txt` (modulo a documented timestamp normalisation pass) reflects the parity-suite-as-oracle design. Anything weaker — semantic equivalence, structural equivalence — leaves room for subtle drift. Byte-equivalence catches every regression in render output. The normalisation pass is documented so reviewers know exactly what is allowed to differ.

The state-file mapping doc (`parity-fixtures/orchestrate-coach.md`) is itself an artifact: it survives as the historical record of what `orchestrate-state.json` carried, so future contributors can read coach's `decisions.jsonl` against an explicit reference rather than reverse-engineering from logs. This is the same pattern used in C0's `event-semantics.md` — semantics frozen as a contract document alongside the schemas.
