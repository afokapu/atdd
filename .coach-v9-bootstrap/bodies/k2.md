## Scope

### In Scope

This issue ships the two missing renderers in `src/atdd/coach/commands/spawn_harness_blocks.py` so `atdd spawn` (`#K1`) can include all three substrate v12 §8.2 rule-ID-rich blocks in the launch prompt. The third renderer (`render_security_rules_block`) ships today (issue `#422`); K2 mirrors its field-mapping pattern for WMBT-acceptance and train-acceptance rules.

- **`render_wmbt_rules_block(rules, *, coach_phase)`** — yields one `wmbt_urn` entry per distinct WMBT in scope and one `rules` entry per acceptance-derived rule under that WMBT, with field mapping `id`, `acceptance_urn`, `purpose`, `expectations[]`, `harness_type`, `signal_metric` per substrate v12 §8.2 example.
- **`render_train_rules_block(rules, *, coach_phase)`** — yields one `train_urn` entry per train and one `rules` entry per train-acceptance-derived rule with field mapping `id`, `purpose`, `expectations[]` (no `acceptance_urn` / `harness_type` / `signal_metric` because train acceptances bind through the train, not directly to a harness).
- **Phase filtering** — both renderers only emit rules whose `RuleMetadata.phase` matches the `coach_phase` argument. Rules at other phases are dropped silently (no zero-rendered placeholders).
- **Spawn integration** — `atdd spawn` (per `#K1`) calls all three renderers and embeds each block under sections `wmbt_rules:`, `train_rules:`, `security_rules:` in the rendered launch prompt, in that canonical order per spec §7.1.
- **Unit tests** against fixture `RuleMetadata` instances exercising: pure-WMBT scope, pure-train scope, mixed scope, multi-phase fixture filtered down to one phase, empty scope (block omitted).

### Out of Scope

- The `render_security_rules_block` renderer — already ships today via `#422`. K2 only adds the parallel WMBT and train renderers.
- The substrate `RuleMetadata` dataclass and rule registry — stable substrate v12 contracts; K2 reads from them but does not modify them.
- Selecting which rules are in scope for a given (issue, phase) — that selection logic is the responsibility of `bind_rule()`'s registry walking and the spawn integration in `#K1`. K2 only renders the rules the caller hands it.
- `atdd spawn` CLI surface itself — owned by `#K1`. K2 is purely the harness-block renderer module.
- The persona prompt template structure (`prompts/persona/<persona>.prompt.yaml`) — owned by `#N3` for reviewer prompts and other tracks for non-reviewer personas.

### Dependencies

- `#K1` — `atdd spawn` calls the three renderers; without K1's wrapper, K2's renderers have no production caller.
- `#C0` — `runtime-event.schema.json` and `event-semantics.md` are referenced by spawn but not directly by these renderers.
- Existing module: `src/atdd/coach/commands/spawn_harness_blocks.py::render_security_rules_block` — the parallel pattern.
- Substrate v12 §8.2 — the field-mapping authority for all three blocks.

## Context

### Problem Statement

| Aspect | Current | Target | Issue |
|--------|---------|--------|-------|
| Substrate spawn-harness blocks | Only `render_security_rules_block` ships (one of three) | All three blocks render — `wmbt_rules`, `train_rules`, `security_rules` | Without all three, agents under spawn don't see WMBT-acceptance or train-acceptance rule-IDs in scope, so they can't reference canonical rule-IDs in commits or reviewer reports |
| Phase filtering of rules | No filtering — security renderer emits whatever the caller hands it | Both renderers filter by `RuleMetadata.phase == coach_phase` | Without phase filtering, an agent at GREEN sees PLANNED-phase rules in its harness and either ignores them (noise) or addresses them (wrong phase, scope creep) |
| Field-mapping consistency | Security renderer's mapping is the de facto authority; the WMBT and train shapes risk drift | All three renderers follow substrate v12 §8.2's field-mapping example verbatim | Per spec §7.1, the renderers are the seam where substrate's rule-ID payoff reaches the agent prompt — drift here corrupts every downstream agent feedback loop |
| Spawn-prompt block ordering | Implicit | Explicit canonical order: `wmbt_rules:` then `train_rules:` then `security_rules:` per spec §7.1 layout | Without canonical ordering, the byte-equivalence assertion in the parity test suite (`#K5`) cannot hold |

### User Impact

The "user" of this issue is every spawned agent (planner, tester, coder, reviewer) who needs to recognise the canonical rule-IDs that bind their work to the substrate. Per spec §7.1, the harness's rule-ID context block is what enables the agent to reference rule-IDs by canonical name in commits, in reviewer reports, and in `atdd agent ask` calls. Without `wmbt_rules:` and `train_rules:` blocks, the agent only sees security-derived rules — which is a fraction of the rule registry.

Per spec §6.3, the per-phase reviewer specifically asks "All declared acceptances covered? Tests fail for the *right* reason?" The reviewer can only answer this question crisply when its harness includes the WMBT-acceptance rules in scope; K2 ships the renderer that puts them there. Per substrate v12 §8.2, this is the documented integration point — the renderers are not novel infrastructure but the natural extension of the existing security renderer.

The lived pain today: in the v8 coach prototype, the test agent at RED phase received a launch prompt with security rules but no WMBT-acceptance rules. The agent could not articulate which acceptance criteria its tests were intended to satisfy because the rule-IDs that codify those criteria were absent from the prompt. Reviewer feedback then cited "test doesn't exercise the contract" without a rule-ID anchor, forcing manual lookup. K2 closes this loop.

### Design Anchor

K2 is a deliberate parallel to a shipped pattern. The security renderer (`render_security_rules_block`) was shipped by `#422` with full field mapping and phase filtering as a single unit. K2 ships the WMBT and train parallels as a single unit — same module, same naming convention, same field-mapping discipline.

The three blocks are kept distinct (rather than unified into one `rules:` block) because their field shapes differ. WMBT-acceptance rules carry `acceptance_urn`, `harness_type`, `signal_metric`; train-acceptance rules carry only `id`, `purpose`, `expectations`; security-derived rules carry `security_urn`, `threat`, `mitigation`. Substrate v12 §8.2 deliberately preserves these shape differences in the harness so agents can reason about each rule kind in its native shape.
