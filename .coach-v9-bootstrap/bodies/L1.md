## Scope

### In Scope

L1 lays the runtime foundation for the `observe-and-correct` wagon: a sidecar process per agent that tails output, watches the worktree, loads detection rules from a registry, dispatches corrections, and isolates rule-level faults. The downstream rule packs (#L2 protocol rules, #L3 token threshold, #L4 babysit-absorbed, #L5 substrate-aware) all plug into this skeleton.

- Create `src/atdd/coach/commands/observer.py` with subcommands `run`, `attach`, `status`, `aggregate-approve`. (`status` and `aggregate-approve` get their full bodies in #L6 and #L7; this issue stubs them and lights up `run`/`attach`.)
- Implement `atdd observer run --agent-id <id> [--rules-dir <path>]` per spec §5.4 — tails `.atdd/runtime/agents/<id>/output.log`, watches the worktree, runs detection rules.
- Implement `atdd observer attach --agent-id <id>` per spec §5.4 — prints recent observations for the named agent.
- Implement the three correction injection paths per spec §8.2:
  1. **CLI return-path** (default) — emits the correction back through the agent's CLI return channel.
  2. **Multiplexer send-keys** — delivers correction text via `src/atdd/coach/utils/multiplexer.py` (cmux/zellij/tmux backends, already shipped) for stuck agents.
  3. **Kill and respawn** — terminates the agent process and triggers respawn through coach for catastrophic failures.
- Build a rule registry that discovers `.atdd/observer/rules/*.yaml`, loads them in alphabetical order, and exposes them to the evaluation loop. Each rule resolves its rule_id via `bind_rule()` per the substrate.
- Per-rule fault isolation: a rule that raises an unhandled exception during evaluation is caught, logged with its rule_id, marked faulty for the run, and does NOT crash the observer or affect other rules' evaluation.
- Order-independent evaluation: rules cannot depend on side effects of other rules' evaluation. Loading is alphabetical for determinism but evaluation outcome is invariant under rule re-ordering.
- Rule-load errors surface visibly: a malformed or unbindable rule emits a one-time stderr warning AND appends a record to `corrections.jsonl` with `meta: rule_load_error` so operators see the failure rather than silently missing detections.
- Corrections written to `.atdd/runtime/agents/<id>/corrections.jsonl` validate against `correction.schema.json` from #C0 — `agent_id`, `rule_id`, `severity`, `disposition`, `correction_text`, `injection_method`. The default `injection_method` is `cli-return`.

Rule-IDs introduced by this issue: none directly (rules ship in #L2-#L5). The observer infrastructure binds rule_ids via `bind_rule()` at rule-load time.

Schemas this issue conforms to: `correction.schema.json`, `runtime-event.schema.json` from `wagon:freeze-runtime-contracts`.

- The `atdd observer status` dashboard body — stubbed only here; #L6 owns the implementation.

## Context

### Problem Statement

| Aspect | Current | Target | Issue |
|--------|---------|--------|-------|
| Detect-and-correct sidecar | `atdd babysit` polls multiplexer state and applies a fixed handful of patterns from `detect_violation` | Event-driven sidecar tails `output.log`, watches the worktree, runs an extensible YAML rule registry | Polling is lossy on transitions, slow, and the fixed-pattern model can't grow without code edits |
| Correction injection | Babysit can correct via screen-state actions but lacks a structured CLI return-path or a kill-and-respawn escape hatch | Three documented injection paths per §8.2 — CLI return-path (default), multiplexer send-keys, kill-and-respawn | Without all three, certain failure modes (stuck agents, catastrophic process state) cannot be auto-recovered |
| Rule fault isolation | Today's babysit `detect_violation` is a single function — a bug in any clause crashes detection for all clauses | Per-rule isolation: a faulty rule is logged with its rule_id, marked faulty for the run, and does not affect other rules | Without isolation, rule additions become high-risk and the registry cannot grow |
| Rule discoverability | Detection logic is hard-coded in `commands/babysit.py` | Rules discovered from `.atdd/observer/rules/*.yaml`; operators can author and disable rules without code changes | Without YAML-discovery, the substrate-aware bridge rules (#L5) and any team-specific rules cannot be authored without toolkit edits |

### User Impact

The "user" of this issue is every coach-orchestrated agent (planner/tester/coder/reviewer) and the operator running `atdd coach`. Today, the babysit sidecar polls and applies a fixed pattern set — the fixed-pattern model is exactly what coach v9 is designed to obsolete (per spec §1, motivation 3: "Trust-based protocol. `detect_violation` catches a fixed handful of patterns"). Without L1, the rule packs in #L2-#L5 have nowhere to land and the rest of Track L is blocked.

After L1 lands, downstream agents and tools can author detection rules as YAML at `.atdd/observer/rules/`, the observer discovers and runs them, and corrections flow through the structured injection paths. Fault isolation means the registry can grow without each new rule being a deployment-blocking risk. Per spec §8.5, this is one layer of the compliance budget — observer rules catch protocol violations in real time, ahead of tier-1 validators.

The lived observation: babysit's "fixed handful of patterns" (`.atdd/` hand-edit, `--status REFACTOR` SMOKE-skip) catch real protocol violations today, but each new pattern requires a babysit-internal edit. The L track absorbs those existing detections (#L4) but lifts them into the extensible registry that L1 establishes — same behavior, different substrate.

### Design Anchor

L1 sits at the boundary between the coach state machine (Track J) and the rule-payload tracks (#L2-#L5). The skeleton has zero detection-rule body of its own — it owns only the runtime, the registry, the injection paths, and the fault-isolation contract. This separation means each rule pack can develop independently against a stable observer surface, and per-rule unit tests do not need to spin up multiplexer state.

The three injection paths reflect three failure-mode classes: structured feedback into a still-functioning agent (CLI return-path), unstructured nudge into a stuck agent (send-keys), and reset of a broken agent (kill-and-respawn). Spec §8.2 documents them as a hierarchy; L1 implements them as peer dispatchers selectable per correction.

Rule fault isolation and order-independence are explicit because they are non-obvious consequences of the registry pattern. Without them, a single buggy rule could silently mask the rest of the registry — exactly the failure mode the rule_id system is designed to prevent. The `meta: rule_load_error` correction line is the visible trail.

## Acceptance

- `acc:observe-and-correct:P001-UNIT-001-observer-run-tails-log`: `atdd observer run --agent-id <id>` starts and tails the agent's `output.log`, watches the worktree, and discovers/loads detection rules from `.atdd/observer/rules/*.yaml`.
- `acc:observe-and-correct:P001-UNIT-002-correction-fires-and-writes`: A simulated detection rule fires and writes a correction record to `.atdd/runtime/agents/<id>/corrections.jsonl` validating against `correction.schema.json`; the default `injection_method` is `cli-return` per §8.2.
- `acc:observe-and-correct:P001-UNIT-003-attach-prints-recent-observations`: `atdd observer attach --agent-id <id>` prints recent observations for the named agent including rule_id, timestamp, and correction_text per observation.
- `acc:observe-and-correct:P001-UNIT-004-rule-failure-isolation`: A rule that raises an unhandled exception is caught, logged with its rule_id, marked faulty for the remainder of the run, and does NOT crash the observer or affect other rules' evaluation.
- `acc:observe-and-correct:P001-UNIT-005-rule-loading-order-independent`: Rules load alphabetically but evaluation outcome is invariant under reverse load order; rules cannot depend on side effects of other rules' evaluation.
- `acc:observe-and-correct:P001-UNIT-006-rule-load-error-surfaced`: A malformed rule produces a one-time stderr warning AND a `corrections.jsonl` entry with `meta: rule_load_error` referencing the rule path; the observer continues with remaining well-formed rules.
- `acc:observe-and-correct:P001-UNIT-007-three-injection-paths-available`: All three correction injection paths from §8.2 are implemented and selectable per correction — CLI return-path, multiplexer send-keys (via `src/atdd/coach/utils/multiplexer.py`), and kill-and-respawn (via coach respawn).
